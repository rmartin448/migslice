# migslice

Pulls a single migration's SQL out of a concatenated migration stream,
without loading the whole stream into memory.

## The problem

Some workflows end up with all your SQL migrations glued into one file:
a squashed history checked into the repo for review, a vendor-shipped
schema bundle, a dump generated by a script that walks a migrations
directory and cats everything together. Once they're one file, finding
the SQL for a single migration means either grepping and guessing at the
boundaries, or opening a file that might be tens of thousands of lines
long in an editor.

migslice assumes the concatenated file uses a marker comment to separate
migrations:

```sql
-- migrate: 0001_create_users
CREATE TABLE users (
    id INTEGER PRIMARY KEY,
    email TEXT NOT NULL
);

-- migrate: 0002_add_login_at
ALTER TABLE users ADD COLUMN login_at TIMESTAMP;

-- migrate: 0003_index_email
CREATE UNIQUE INDEX idx_users_email ON users (email);
```

Given that, `migslice` finds the block you asked for and prints exactly
that, nothing else.

## Usage

```sh
$ migslice 0002_add_login_at dump.sql
ALTER TABLE users ADD COLUMN login_at TIMESTAMP;

$ migslice --list dump.sql
0001_create_users
0002_add_login_at
0003_index_email
```

To pull more than one migration at a time, use `--from` and `--to` for an
inclusive range instead of a single id. Either bound can be left off:

```sh
$ migslice --from 0002_add_login_at --to 0003_index_email dump.sql
ALTER TABLE users ADD COLUMN login_at TIMESTAMP;

CREATE UNIQUE INDEX idx_users_email ON users (email);

$ migslice --from 0002_add_login_at dump.sql   # runs through the end
$ migslice --to 0002_add_login_at dump.sql     # starts at the first migration
```

The range is resolved by the order ids appear in the stream, not by
sorting or comparing them, so it works no matter what the ids look like.
If either bound isn't found in the stream, nothing is printed and
`migslice` exits 1.

It also reads from stdin, so it works in a pipeline:

```sh
$ cat dump.sql | migslice 0001_create_users
CREATE TABLE users (
    id INTEGER PRIMARY KEY,
    email TEXT NOT NULL
);
```

If the id isn't found, it exits with status 1 and says so on stderr
instead of printing nothing and leaving you to wonder.

## Why streaming matters here

The whole reason to reach for this tool instead of `grep -A` is that the
input can be large - a squashed history for a mature project can run to
hundreds of thousands of lines. `migslice` never calls `.read()` on the
input; it iterates over it line by line, and only holds the lines of the
one migration currently being assembled. Once the requested id is found,
it stops pulling from the stream at all, so a match near the top of a
huge file doesn't cost you a read of the rest of it.

## Install

No dependencies beyond the standard library. From a checkout:

```sh
pip install .
```

which gives you the `migslice` command, or run it in place with
`python -m migslice`.

## Status

Early. The marker format (`-- migrate: <id>`) is the only one supported
right now - see the roadmap for what's planned.
